# M4 — approved opt-in automatic worker

Branch `codex/m4-staging-worker`, based on PR #197.

Production now wires the read-only evaluator, restricted writer and durable Fleet publication recovery when PostgreSQL, telemetry, signing/object storage and replay support exist. Policies remain off unless their deployed, independently approved version explicitly enables auto_staging. The worker checks immediately, then every ten seconds, without overlapping ticks. It recovers existing publication first, requires an ACTIVE completed source, excludes already staged IDs and pages at most 16 durable FP candidates per tick. Low-share candidates advance the cursor so later rules can be evaluated. A read-only precheck avoids compiler snapshots for low-share candidates; the writer then independently rechecks fresh scope/counts/authorization before signing. At most one derivation is recorded per tick, with a two-minute work deadline; no reset/re-enforcement path exists.

`Run` integration with real PostgreSQL reports, real Rust compilation/signing and real Fleet presence notifications proves automatic FP candidate → durable action → signed bundle → linked rollout/notice, process-instance recovery, no second action on retry, stop on cancellation and preservation after simulated ACK. A second case proves disabled policy does no match query/deploy and a below-5% first rule does not starve a qualifying second rule. The existing writer fixture adds a second managed rule for that scenario, retaining all prior assertions.

Limits: match telemetry is a test reader, approval-bound replay is a proof fixture, and node ACK is simulated. This is not the final ClickHouse/replay-executable/agent/NGINX chain or proof that an actual node changes verdict within five minutes. A large candidate set, slow compiler/query or offline node can exceed that deadline; the test timing is a scoped lab observation. Reviewer notification UI/read API and that actual activation evidence remain unfinished.
