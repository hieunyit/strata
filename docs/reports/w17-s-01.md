# W17-S-01: CRS paranoia level 2 per policy (enforce + shadow)

Done when (plan): a route can run PL2 in shadow; plugin exclusions
(WordPress, Drupal…) can be imported. PR #269 added the engine, bundle and
import. The second PR adds the policy fields to the admin API and the UI
(below). Plugin exclusions come in the third.

PO decision (19/10): two levels per policy, not one.

## Model

| Policy field | Range | Default | Meaning |
| --- | --- | --- | --- |
| `crs_paranoia` | 1–4 | 1 | CRS rules up to this level run and block as usual |
| `crs_paranoia_shadow` | `crs_paranoia`–4 | `crs_paranoia` | rules above the enforced level, up to this one, run and are reported (Event ID `EVT-`, action `log`), but their score is kept apart and they never block, like the signature pack in `signatures: shadow` |

Rules above `crs_paranoia_shadow` do not run. Rules without a level (protocol,
Strata, signatures) are not affected. "PL2 in shadow" for a route means
`crs_paranoia_shadow: 2` on its policy.

Bundle (see `docs/design/control-file.md`): bit 6 of policy byte 62,
section 13 `PARANOIA` (codec `SPL1`), target code 30 `basename`, and
transformation code 17 `escape_seq_decode`. Engines from before this change
refuse all four, so **upgrade the module on every node first**. When no
policy goes past level 1, the compiler leaves the higher rules out of the
bundle, so default bundles are byte-for-byte what they were.

## Import (`make crs-import`, `--max-pl 2`)

| | Before | Now |
| --- | ---: | ---: |
| Imported | 150 (PL1) | **228** (150 PL1, unchanged, + 78 PL2) |
| PL1–2 detection rules active by default | — | 237, 96% imported |

To reach the go-ftw target, the importer gained:

- `t:escapeSeqDecode` → `escape_seq_decode` (port of Coraza v3.8.1, with its
  test vectors): 932210, 932300, 932310, 932320.
- `REQUEST_BASENAME` → `basename`: 920200, 920201, 942101.
- A 2-link chain "regex with `capture`, then `TX:1 @rx ^X$`" is folded into
  the first regex, with its first group replaced by `X`: 942521. **It can
  match more than CRS.** CRS checks the group of the first match only, and
  the fold accepts any match. This shows as one failing negative test,
  942521-16 (prose about SQLi). Noted in `docs/crs-import-report.md`.

Still left out at PL2: 920650, 931130 (comparing captured values with Host),
932205/932207 (3-link chains over TX), 942130/942131 (backreferences).

It depends on PR #268 (`(?s)` on CRS regexes, a PL1 newline bypass). Without
it, PL2 CRS test 942522-7 ("New line bypass") fails.

## Benign false positives at PL2 (`strata-rules report --rules rules/crs --pl 2`)

| | PL1 | PL2 enforced |
| --- | ---: | ---: |
| Benign requests matched (of 3000) | 0 | **275 (9.2%)** |
| Blocked SQLi / XSS / CMDi / LFI | 76.2 / 75.2 / 94.2 / 97.2% | 94.3 / 86.8 / 96.9 / 98.5% |

Rules behind the benign matches: 942440 (142, SQL comment sequences in
pilot tokens), 942380 (75), 942200 (46), 932200 (12), 942480 (2). So PL2
belongs in shadow (events only) until each route's FP table (W10-S-01) has
been reviewed. Enforcing it on a route needs PO approval and its own
exceptions.

## Open for the PO: Vault signing size

Measured on 19/10 with core 0.2.2 + signature pack, deployed through the lab
signer, before the last 8 PL2 rules were added:

| Bundle | Size |
| --- | ---: |
| No PL2 policy | 21.6 MB |
| One policy with PL2 (shadow or enforced) | **29.4 MB**, above Vault transit's 25,165,824-byte request limit |
| With PL2, without the Hyperscan block-mode copy (#27) | 16.7 MB |

A default bundle is unaffected because PL2 rules are left out. With PL2 on
any policy, the KMS signer refuses the bundle with a clear error, and the
file signer works. Options, for the PO to choose:

1. Drop the block-mode Hyperscan copy when a bundle is over the limit.
2. Raise the limit (Vault `max_request_size`).
3. Keep the block-mode copy for the core pack only.

## Admin API and UI (second PR)

- `PolicySpec.crs_paranoia` (11) and `crs_paranoia_shadow` (12) in
  `proto/strata/admin/v1/policy.proto`, `docs/spec/admin.swagger.json`, and
  the generated TypeScript. Validated like the compiler: 1–4, shadow ≥
  enforce. Defaults are stored as absent, so the JSON and the replay digest
  of a policy that doesn't use them stay unchanged.
- Changing a level makes a new version, like any other spec change: draft,
  replay, four-eyes approval, deploy.
- Policy editor: two selects (enforced level, shadow level; the shadow
  list starts at the enforced level). The YAML keys `crs_paranoia` and
  `crs_paranoia_shadow` are kept in sync with them. A note on false
  positives (~9% of benign requests at PL2) and on upgrading modules
  first. The version diff shows both levels in the General block.
- Tests: `control-plane/policy` (validation, normalization, compiler
  input; the real `strata-compile` writes `SPL1` and the PL2 rule only when
  a policy asks for them), `control-plane/admin/policy_paranoia_test.go`
  (API round trip, defaults stored as absent, invalid levels refused), and
  `ui/src/__tests__/PolicyParanoia.test.tsx`. No migration needed.
