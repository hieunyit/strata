# W17-S-01: CRS paranoia level 2 per policy (enforce + shadow)

Done when (plan): a route can run PL2 in shadow; plugin exclusions
(WordPress, Drupal…) can be imported. PR #269 added the engine, bundle and
import. The second PR adds the policy fields to the admin API and the UI
(below). Plugin exclusions come in the third.

PO decision (19/10): two levels per policy, not one.

## Model

| Policy field | Range | Default | Meaning |
| --- | --- | --- | --- |
| `crs_paranoia` | 1–4 | 1 | CRS rules up to this level run and block as usual |
| `crs_paranoia_shadow` | `crs_paranoia`–4 | `crs_paranoia` | rules above the enforced level, up to this one, run and are reported (Event ID `EVT-`, action `log`), but their score is kept apart and they never block, like the signature pack in `signatures: shadow` |

Rules above `crs_paranoia_shadow` do not run. Rules without a level (protocol,
Strata, signatures) are not affected. "PL2 in shadow" for a route means
`crs_paranoia_shadow: 2` on its policy.

Bundle (see `docs/design/control-file.md`): bit 6 of policy byte 62,
section 13 `PARANOIA` (codec `SPL1`), target code 30 `basename`, and
transformation code 17 `escape_seq_decode`. Engines from before this change
refuse all four, so **upgrade the module on every node first**. When no
policy goes past level 1, the compiler leaves the higher rules out of the
bundle, so default bundles are byte-for-byte what they were.

To reach the go-ftw target, the importer gained:

- `t:escapeSeqDecode` → `escape_seq_decode` (port of Coraza v3.8.1, with its
  test vectors): 932210, 932300, 932310, 932320.
- `REQUEST_BASENAME` → `basename`: 920200, 920201, 942101.
- A 2-link chain "regex with `capture`, then `TX:1 @rx ^X$`" is folded into
  the first regex, with its first group replaced by `X`: 942521. **It can
  match more than CRS.** CRS checks the group of the first match only, and
  the fold accepts any match. This shows as one failing negative test,
  942521-16 (prose about SQLi). Noted in `docs/crs-import-report.md`.

Still left out at PL2: 920650, 931130 (comparing captured values with Host),
932205/932207 (3-link chains over TX), 942130/942131 (backreferences).

It depends on PR #268 (`(?s)` on CRS regexes, a PL1 newline bypass). Without
it, PL2 CRS test 942522-7 ("New line bypass") fails.

Rules behind the benign matches: 942440 (142, SQL comment sequences in

## Open for the PO: Vault signing size

Measured on 19/10 with core 0.2.2 + signature pack, deployed through the lab
signer, before the last 8 PL2 rules were added:

| Bundle | Size |
| --- | ---: |
| No PL2 policy | 21.6 MB |
| One policy with PL2 (shadow or enforced) | **29.4 MB**, above Vault transit's 25,165,824-byte request limit |
| With PL2, without the Hyperscan block-mode copy (#27) | 16.7 MB |

A default bundle is unaffected because PL2 rules are left out. With PL2 on
any policy, the KMS signer refuses the bundle with a clear error, and the
file signer works. Options, for the PO to choose:

1. Drop the block-mode Hyperscan copy when a bundle is over the limit.
2. Raise the limit (Vault `max_request_size`).
3. Keep the block-mode copy for the core pack only.

## Plugin exclusions (WordPress, Drupal…)

The PO chose exclusion rules in the engine (20/10). Part 1 (#275) adds
the engine mechanism: rule flag bit 3, section 14 `EXCLUSIONS`, and the
policy setting `crs_plugins`. Part 2 imports the official CRS plugins:
`make crs-plugins-import`, eight plugins pinned with their sha256 in
`tools/strata-import-crs/crs-plugins.lock`, written to
`rules/crs-plugins/`. Details are in `docs/crs-plugins-import-report.md`.

| Plugin | Rules | Imported |
| --- | ---: | ---: |
| wordpress v1.2.0 | 61 | 58 |
| drupal v1.0.0 | 22 | 21 |
| nextcloud v1.7.1 | 144 | 124 |
| phpmyadmin v1.1.0 | 66 | 36 |
| phpbb v1.0.0 | 15 | 13 |
| xenforo v1.0.0 | 43 | 40 |
| dokuwiki v1.0.0 | 10 | 2 |
| cpanel v1.0.0 | 2 | 1 |

phpMyAdmin keeps 36 of 66 because the section for its old URL format is
skipped under the plugin's default (`url_format=v51`). DokuWiki's admin
section is gated on `ARGS:do`, which can have several values, so its
negation can't be stated exactly and those rules are left out.

How the importer translates the plugins:

- **Removals.** `ctl:ruleRemoveById` and `ctl:ruleRemoveTargetById` become
  IR `exclude` entries. A tag (`ruleRemoveTargetByTag=OWASP_CRS`,
  `attack-sqli`…) is expanded into runs of the CRS rule IDs that carry it.
  A target Strata has no variable for (`TX:…`) is left out and listed in
  the report.
- **`skipAfter` gates.**
  - A gate that depends on the request (WordPress `/wp-admin/`, XenForo
    `/admin.php`, phpMyAdmin `/index.php`) is folded into the rules it
    gates, phase by phase, as its negation. This is only done for
    variables with exactly one value (`path`, `uri`…).
  - Any other gate leaves the rules out. It does not apply them
    everywhere, which would remove more than the plugin does.
- **Plugin options** (`TX:…_enabled`, `url_format`) are decided with the
  plugin's own defaults. For example, Nextcloud's iOS workaround and
  crawler rules are off by default and are left out. The plugin's main
  switch becomes the policy's `crs_plugins`.
- **CRS list options a plugin extends.** For example, Nextcloud adds
  WebDAV methods to `tx.allowed_methods` on its DAV paths. This is
  imported as removing 911100 (methods) or 920420 (content types) when
  the request has one of the added values. That is exact, because those
  rules only check the list.
  - A plugin rule that both extends a list and has `ctl` actions becomes
    two exclusion rules, the second with ID + 100000.
  - Nextcloud also narrows the CRS default methods when crs-setup sets
    none. Strata keeps the CRS defaults instead: it can't narrow.

### The plugins' go-ftw tests (`make test-crs-plugins`)

Each CRS rule a test asserts is compiled alone with the plugin and run
under two policies, with and without the plugin. The gate is that no
test fails because of the plugin. Full results:
`docs/crs-plugins-ftw-report.md`.

| Plugin | Expectations | Pass | Pass only thanks to the plugin | Fail because of the plugin |
| --- | ---: | ---: | ---: | ---: |
| wordpress (PL1 / PL2) | 67 / 222 | 64 / 209 | 30 / 84 | 0 / 0 |
| nextcloud (PL1 / PL2) | 458 / 980 | 436 / 918 | 159 / 269 | 0 / 0 |
| phpmyadmin (PL1 / PL2) | 18 / 19 | 18 / 19 | 14 / 14 | 0 / 0 |

The other failures also fail without the plugin: they are CRS rules
Strata doesn't import, or that behave differently in Strata, not
exclusions. The other five plugins ship no tests with expectations on
rule IDs.

These tests found two errors in the first version of the importer, both
fixed, and both of which removed more than the plugin does:

1. Rules gated by `skipAfter` were imported without their gate.
2. Nextcloud's optional rules, which are off by default, were imported as
   always on.

### On the admin API and the policy editor

- `PolicySpec.crs_plugins` (field 13) in the admin proto, swagger and
  TypeScript. Each name is 1–32 of `a-z 0-9 -`, at most 16, none twice.
  The list is stored sorted, and an empty list is stored as absent.
- Like any spec change, a change makes a new version (draft, replay,
  four-eyes approval, deploy).
- The deploy compiles the policy with the release packs. Plugin rules
  (source `crs-plugin`) are in the core pack, and a plugin that has no
  rules there fails the build with a clear error.
- The policy editor has a checkbox for each of the 8 pinned plugins, kept
  in sync with the YAML key `crs_plugins`. The version diff shows the
  list in the General block.
- Tests: `control-plane/policy` (validation, sorting, compiler input;
  with the real `strata-compile`, section `SXC1` appears only when a
  policy lists the plugin, and a plugin without rules fails),
  `control-plane/admin` (round trip, invalid names refused), and
  `ui/src/__tests__/PolicyParanoia.test.tsx`. No migration.
